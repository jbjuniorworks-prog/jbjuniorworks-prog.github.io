Projeto · govtech SaaS

Plataforma de licenciamento ambiental por município

SaaS multitenant onde prefeituras configuram tipos de licença, empreendedores abrem e acompanham pedidos por um portal, e a IA apoia a análise. Sou dono de uma fatia vertical de funcionalidades — do banco à tela — num time que faz merge contínuo na main.

O sistema tem três públicos — o painel interno da prefeitura, a operadora da plataforma (que confere e libera) e o portal público do empreendedor — e cada recurso é escopado por cidade, sem vazar dados entre municípios. Entreguei desde a modelagem do núcleo de licenciamento até o treinamento de IA de verdade, sempre no mesmo padrão: slice vertical (domínio → dados → apresentação), migrations escritas à mão e verificação rodando de verdade antes de subir.

A regra no centro, a infra por fora

O núcleo de domínio não conhece framework, SQL nem HTTP — o que deixa a decisão de negócio testável e o resto substituível.

domain

Dataclasses, interfaces de repositório e use cases. É onde a decisão de negócio acontece — puro Python.

data

Implementações concretas das portas. Troco o adapter (mock → SQL, stub → OpenAI real) sem tocar no domínio.

presentation

Rotas, schemas e o envelope de erro único em pt-BR. Multitenancy e permissões (RBAC) aplicadas aqui.

web · bff

O Next.js é um Backend-for-Frontend: server actions injetam a sessão no servidor. O navegador nunca fala com a API direto.

Impacto · qualidade & segurança

Auditoria do repositório inteiro

Varri o sistema todo (~43 mil linhas) com seis revisores em paralelo e corrigi 17 achados em 5 PRs — cada um verificado exercitando o caso real, não só compilando. Entre eles: um escalonamento de privilégio em que um convidado conseguia virar super-admin da plataforma, vazamento de pedidos entre municípios e um treino de IA disparado no tenant errado gastando crédito alheio. Foi aqui que virei a lente de "features" para "onde isso quebra".

Como foi feito

monorepo

Três apps, uma base

Workspaces pnpm com packages de tipos, tema e cliente de API compartilhados — trocar um contrato ecoa nos três apps de uma vez.

spec-driven

A spec é a fonte da verdade

Cada rota, evento e ferramenta de IA nasce de uma spec tipada. Dela saem os testes, a doc OpenAPI e o contexto do agente — o CI trava o merge se algo sair de sincronia.

tempo real

Entrega ao vivo

Eventos por WebSocket (Socket.IO) e mapas com rota/ETA levam a posição do entregador até a tela do consumidor em tempo real.

ia

Assistente que age

Um agente de compras com tool-calling busca produtos e monta pedidos, ancorado no contexto gerado das specs para não alucinar chamadas de API.

Como eu trabalho

O código certo é o que roda — e não vaza

Alguns hábitos que carrego pra qualquer time.

// contrato primeiro

Backend antes do front

Fecho e valido o contrato da API antes de desenhar a tela. Decisão que muda schema? Pergunto antes de codar.

// verificação real

Nada de "deve funcionar"

Só considero pronto o que verifiquei rodando de verdade — subo a stack, exercito o caso e testo os cenários de falha.

// migrations à mão

Migrations encadeadas, sem surpresa

Alembic escrito à mão e encadeado no head atual. Depois de sincronizar com a main, re-checo os heads antes de subir.

// revisão

Reviso o diff inteiro

Leio a mudança toda e passo um revisor independente antes de abrir o PR. Git em inglês, Conventional Commits.

// da main atualizada

Sempre do código mais atual

O time faz merge contínuo. Começo e integro sempre da main sincronizada — começar desatualizado é retrabalho garantido.

// spec-driven

Da especificação ao código

Em features médias/grandes, saio do spec para o plano e para as tasks (Spec Kit) — o "porquê" fica versionado no repo.
